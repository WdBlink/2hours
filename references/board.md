# 看板与文字批注

`board.json` 是当次报告的目录摘要，不放在技能代码中。卡片外显示与详情一致的 ID，其 ID 与 manifest / AM 面板一致；正文仍由 AM 渲染，构建脚本保留图表、表格和来源。每次运行只需写数据。

```json
{
  "title": "本次工作与阅读",
  "period_label": "本次回看范围",
  "review_label": "本次审阅日期",
  "coverage_label": "实际读取的会话与文章数量",
  "cards": [
    {"id":"A1", "area":"work", "lane":"decide", "label":"实验",
     "title":"需要选择的具体问题", "value":"2", "unit":"个方案",
     "state":"预算待定", "context":"报告范围与关键限制"},
    {"id":"A2", "area":"reading", "label":"文章主题",
     "title":"文章标题或准确的主题", "summary":"文章在说什么，最值得读的内容是什么。",
     "state":"全文已读；作者结论尚未独立复核", "context":"正文区分作者观点、用户标注与 Agent 推断"}
  ]
}
```

`area` 是 `work` 或 `reading`。两区分别显示 Agent 工作与 Cubox 阅读。工作卡的 `lane` 保留 `decide` / `follow` / `result`，分别表示需要判断、继续跟进、结果与来源。阅读卡可省略 `lane`，提供时只接受这三个旧值，但不以工作状态分组。材料数量由实际内容决定，不设总数或每组上限，也不为数量合并无关工作或拆分文章。

桌面将两个区域并列，以留白和分隔建立分区层级。阅读区用自然高度的单列横条逐篇呈现，工作区保留独立卡片。每个条目保留 panel ID、原文入口、详情、文字批注和未审阅曲别针，不合并无关文章。每区显示总数和当前页；窄于 1100px 时用明确的区域按钮切换，按钮仍显示全量数量。

分页前先按视口与材料数量调整列数、宽度和间距。工作区先用 18px 间距，必要时收至 12px；候选列宽下限为 236px，常规目标为 320px。容量按每行实际内容高度测量，148px 只是测量下限，不能裁掉更高的标题或状态。少量卡片的空白扩张上限为 240px，不限制真实内容高度。只有全量材料在可读尺寸内仍放不下时才分页，不以隐藏条目或缩小字体凑一屏。

工作标题保持 18px，阅读标题保持 16px，常规正文至少 14px；移动端正文为 16px。空区明确显示本轮无材料，不编造占位任务。单项极长时允许其局部滚动，低于 500px 高的极短或高缩放窗口允许页面滚动，避免控制不可达。

标题、状态和数字自然换行，不通过缩成小字塞入固定行高。`value/unit` 只用有意义且有来源的数字，没有可省略。`summary` 用于文章内容摘要，卡面最多两行，完整摘要、数字和状态在详情顶部可读。工作卡的正文按 [报告内容合同](report.md) 自足展开；阅读卡正文应给文章内容、用户标注和原文，不能用抓取/处理过程充当阅读内容。`context` 是详情顶部的短提示，不承载核心证据。图示留在详情，不挤压首屏。

详情中的图与正文共同回答卡片的问题。分支条件、当前停点、交接缺口和循环反馈不得在构建后丢失；图注保留来源、状态与推断标识。宽图先拆成各有问题的静态 AM 图或改纵向布局，不缩小到难以阅读。桌面与窄屏都应能读到完整图、比较表和来源，不能依靠 AM 运行时切换补齐事实。阅读卡的知识关联放在文章内容之后，引用真正相关的已读知识条目，不默认链接到 Two Hours 工作卡。

阅读卡的原文按钮来自 `manifest.panels[].source_ids` 对应的 `manifest.sources[]`，只显示 provider 为 `cubox` 且有 HTTPS `url` 的来源。每个链接用对应来源标题作为可访问名称，多个来源全部保留；链接在详情按钮之外，不触发卡片打开。正文继续提供完整引用、标注与精确定位，收藏不构成任务授权。

兼容旧数据时，不需要改动面板 ID 或正文。缺省 `area` 仅在全部登记来源均为 Cubox 时推断为阅读，其余视为工作。混合会话和文章来源的旧卡需要在新的报告或预览数据中明确写 `area`，不能靠标题关键词猜测。旧 `title` 保留作浏览器标题；旧 `subtitle` 仍可输入，但不再展示为首屏标语。范围、日期和覆盖信息改为顶部紧凑信息行。构建继续校验 ID 与所有面板一一对应、分组合法、文本转义和禁止主动内容。

正常入口为 `run.py render --run RUN`，发现 board.json 后自动把 AM 产物保存为 report.am.html，并生成最终 report.html。已有受检 AM 内容也可先存为 report.am.html，调用 `build_board.py --run RUN`。已有 report.html 不允许覆盖，换版需新建运行，旧录音、批准与回执不搬成新指令。

## 审阅状态

- 每卡的 `read`、`comment` 与 `revision` 写入 `review-state.json`，重开页面可恢复。
- “标记已审阅”是明确动作，打开窗口本身不算读完。待审阅卡片显示曲别针。
- “保存意见”只持久化。未保存输入有浏览器草稿与关闭提醒，保存失败不清空输入。
- 同一卡片另一页面已更新时，旧 revision 被拒绝，用户可先复制当前文本再刷新核对。

## 提交与分发

右上“汇总意见”默认展开已保存的文字意见，提交操作位于意见列表之前。尚有未保存草稿时先提示保存。用户点击“提交给 AI 整理”时，服务校验展示版本，将原话、panel ID 与标题写入 `written-items.json`，并输出 `comments_submitted` 事件。重复提交相同内容不会制造重复事件。

服务断开时显示恢复指引与重试入口，不把读取失败当作无意见。用原运行目录和原端口 `review_bridge.py --run RUN --port PORT` 恢复后，刷新原地址重新建立连接；相同地址的浏览器草稿会恢复，旧连接 token 仍被拒绝。

默认人工模式下，宿主收到事件后逐项理解，和口述合并成统一审核草案；有结果后，右上入口切换为“集中审核”。保存意见不授权派发。用户显式选择自动模式后，只有对应提交输入中的明确任务可按该模式处理，去向或目标不明确的条目单独待澄清。提交本身仍由宿主解析和校验，不由页面直接向会话发消息。模式、绑定和失败恢复细节见 [设置合同](settings.md)。新提交会让旧草案失效，必须重新 prepare-review；已有最终确认后，新增意见用下一轮运行处理，不能覆盖已批准快照。

`dispatch.py prepare-review` 可消费纯文字、纯口述或两者。只保存但未提交的文字不进入草案。默认人工模式下，未审核口述只用于草案；统一审核沿用 Blurt 的专注布局，左侧为任务目录，中间展示大图与缩略图，右侧以正文形式展示原话、任务和执行去向。编辑字段随内容自动伸展；截图下方选择暂缓或纳入执行，顶栏只有一次最终确认。窄屏隐藏目录，通过上一项、下一项切换，并按证据、编辑区顺序纵向排列。自动模式仍保留待澄清条目和可追溯的材料绑定。草稿按 review_id 保留，材料变化时不静默套用旧编辑。

集中审核样式由 `review_bridge.py` 与交互代码一起加载，使用独立选择器避免旧报告样式冲突。已有报告重新启动服务后可使用新版审核界面，不改写冻结的报告、来源材料或批准。
